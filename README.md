# Repo Issue Investigation Assistant

Investigate issues in a local Python repository using a React interface and an
AI workflow. The assistant searches source files, produces a report with code
references, and pauses for human review. Users can accept the report, request a
revision, or reopen a previous investigation.

Reports include a likely cause, supporting file and line references, a suggested
fix, test cases, and uncertainties. The assistant reads source files without
executing the target repository or applying changes.

## Features

- Issue submission, progress polling, and investigation history.
- Bounded keyword search and source-file reading.
- Structured reports generated by Google Gemini and validated with Pydantic.
- Human review and feedback-driven revision through LangGraph interrupts.
- SQLite records and durable checkpoints that support review after a restart.
- Mock mode for trying the application without an API key.

## Getting started

Use Python 3.12+ and Node.js 22.12+. The application has been validated on Windows
with Python 3.13.5 and Node.js 22.17.0. Dependency versions are pinned in
`backend/requirements.txt` and `frontend/package-lock.json`.

From the project root, install the backend dependencies and create the configuration:

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r backend\requirements.txt
Copy-Item .env.example .env
```

Start the backend:

```powershell
.\.venv\Scripts\python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

In a second terminal, start the frontend:

```powershell
cd frontend
npm ci
npm run dev
```

Open [the application](http://127.0.0.1:5173) or
[the API documentation](http://127.0.0.1:8000/docs).

On macOS/Linux, use `.venv/bin/python` and `cp .env.example .env`. These platforms
have not been verified. Run a single backend worker. The sample repository does
not need its own server running because the investigator reads its files as text.

## Configuration

The default configuration uses `LLM_MODE=mock`, which requires no API key. Mock
mode produces deterministic responses for the sample issues and is labeled in
the interface. Mock revisions record feedback without generating a new AI diagnosis.

For live model calls, create a key in [Google AI Studio](https://aistudio.google.com/apikey)
and update the project-root `.env`:

```dotenv
LLM_MODE=gemini
GEMINI_API_KEY=your-api-key
GEMINI_MODEL=gemini-3.1-flash-lite
```

Restart the backend after changing the configuration. Keep the key in the backend
`.env`, which is gitignored. Live requests send issue text, repository excerpts,
and review feedback to Gemini and consume the provider's quota. Provider errors
are shown in the application; failed requests do not switch to mock mode.

| Variable | Default | Purpose |
| --- | --- | --- |
| `LLM_MODE` | `mock` | Choose `mock` or `gemini` |
| `GEMINI_API_KEY` | Empty | Required for Gemini mode |
| `GEMINI_MODEL` | `gemini-3.1-flash-lite` | Model used for live investigations |
| `REPO_ROOT` | Project-root `sample_repo/` | Repository available to the assistant |
| `DATA_DIR` | Project-root `data/` | Application records and checkpoints |

Use absolute paths for directory overrides. Keep evaluation answers outside
`REPO_ROOT`, and keep the repository stable while an investigation is running.
Each investigation retains its original mode, model, and repository location.

## Try an investigation

1. Select **New investigation** and choose the **Pagination** sample.
2. Submit the issue and wait for a report.
3. Open the cited evidence to inspect the pagination calculation in `catalog.py`.
4. Request a revision, such as: "Add tests for the last partial page and an empty page."
5. Review the revised report, accept it, and reopen it from **History**.

The included Tiny Catalog sample also contains null-handling and filtering bugs.
`evaluation/issues.json` includes those scenarios, a vague issue, and an issue
that cannot be resolved from the available repository.

## Architecture

```text
React UI --HTTP requests and polling--> FastAPI --> LangGraph
                                          |            |
                                 investigations.db  checkpoints.db
                                 history and status  workflow state

START -> plan -> collect -> analyze --additional evidence needed--> collect
                              |
                            review [interrupt]
                              | accept -> END
                              | feedback -> revise -> review
```

The graph permits an initial search and at most two additional search rounds.
Revisions use existing evidence. Reports are checked against retrieved snippet
IDs, paths, and line ranges before being presented for review.

Application records and workflow checkpoints have separate responsibilities.
SQLite application records provide history and status; LangGraph checkpoints
preserve execution state. The investigation ID is the checkpoint thread ID.
Review submissions include a report version to reject stale decisions, and
recovery checks prevent an already-consumed revision from being applied twice.

| Location | Responsibility |
| --- | --- |
| `backend/app/repository.py` | Safe file listing, keyword search, and bounded reads |
| `backend/app/llm.py` | Gemini integration and mock responses |
| `backend/app/models.py` | Request, report, and citation validation |
| `backend/app/workflow.py` | Search, analysis, review, and revision graph |
| `backend/app/storage.py` | Application records |
| `backend/app/service.py` | Background execution and checkpoint recovery |
| `backend/app/main.py` | FastAPI endpoints |
| `frontend/src/` | React interface |
| `sample_repo/` | Example Python repository |
| `evaluation/` | Sample issues, separate expected answers, and evaluation tools |

## API

| Endpoint | Purpose |
| --- | --- |
| `GET /api/health` | Current mode, model, and repository label |
| `POST /api/investigations` | Create an investigation with an `issue` string |
| `GET /api/investigations?limit=20&offset=0` | List investigation history |
| `GET /api/investigations/{id}` | Fetch status, evidence, report, and errors |
| `POST /api/investigations/{id}/review` | Accept or request revision with `decision`, `feedback`, and `report_version` |

Create and review requests return HTTP 202. Invalid input returns 422, missing
investigations return 404, and stale or unavailable review decisions return 409.
Revision requests require nonblank feedback.

## Testing and evaluation

From the project root:

```powershell
.\.venv\Scripts\python -m pytest -q
.\.venv\Scripts\python -m evaluation.run
```

Build the frontend:

```powershell
cd frontend
npm run build
```

Run the live sample evaluation using the configured Gemini key:

```powershell
.\.venv\Scripts\python -m evaluation.run --live --output evaluation/results-live.json
```

Add `--case pagination` to evaluate one issue. Live evaluation consumes provider
quota. Expected answers are kept outside the assistant's readable repository and
are never sent to the model. The rubric checks paths, keywords, partial-report
status, and search bounds; reports also need human inspection.

The test suite covers repository boundaries, retrieval limits, structured outputs,
provider failures, bounded retries, persistent review, and restart recovery.
Mock evaluation verifies workflow behavior rather than live diagnosis quality.
See [VERIFICATION.md](VERIFICATION.md) for recorded results and verification limits.

## Limitations

- Supports one configured local Python repository. GitHub repository ingestion
  and authentication are not implemented.
- Intended for local, single-user use with one backend worker.
- Diagnoses are hypotheses. Valid references do not prove a cause or a fix is correct.
  Vague issues can still produce overly confident reports; include reproduction details.
- Keyword retrieval can miss relevant code. Inventory is limited to 300 files and
  3,000 scanned entries; evidence is limited to 16 snippets of up to 40 lines and
  5,000 characters each.
- Repository tools exclude links, hidden paths, dependency directories, common
  secret files, binaries, and files over 100 KB. Secret detection is heuristic;
  use a repository without credentials or confidential data.
- Saved evidence can become stale after repository edits. File checks do not
  protect against adversarial concurrent filesystem changes.
- An interrupted model call can repeat after a crash and consume additional quota.
- Fixes and test cases remain suggestions for a developer to verify and implement.
